# 트러블슈팅 주요 개념 섹션 설계

## 목표

개발 지식은 있지만 문서가 다루는 분야에는 익숙하지 않은 독자가 증상과
원인 사이의 흐름을 이해할 수 있도록, 필요한 트러블슈팅 문서에 배경 개념을
맥락과 함께 설명한다.

## 포함 기준

`주요 개념`은 모든 문서에 강제하지 않는다. 증상이나 원인을 이해하려면
특정 도구, 실행 환경, 프레임워크 동작처럼 일반 개발 지식만으로 알기 어려운
전제가 필요할 때만 추가한다. 단순 오타나 설명 없이도 원인을 따라갈 수 있는
문제에는 넣지 않는다.

## 구조

`주요 개념`은 날짜·영역·커밋 메타 정보 다음과 `증상` 사이에 둔다. 섹션
안에서는 개념별로 `### 개념명` 소제목을 사용하며, 기존 번호 문장 규칙은
적용하지 않는다.

각 설명은 다음 흐름을 따른다.

1. 개념의 일반적인 뜻을 전문용어에 기대지 않고 설명한다.
2. 해당 개념이 현재 프로젝트에서 어떻게 동작하는지 설명한다.
3. 그 동작이 이번 증상이나 원인과 어떻게 연결되는지 설명한다.

## 선택과 설명 기준

문제의 인과관계를 따라가는 데 꼭 필요한 개념 2~5개만 고른다. 본문에서
한 번 등장하는 용어를 전부 사전화하지 않고, 모르면 다음 문장을 이해할 수
없는 개념을 우선한다. 처음 보는 독자가 이해할 수 있도록 풀어 쓰며, 설명이
추상적일 때만 짧은 예시를 덧붙인다.

개념 설명도 관찰하거나 확인한 사실에 근거한다. 도구의 일반 동작을 확신할
수 없으면 프로젝트 코드나 공식 문서로 확인하고, 확인하지 못한 내용을
그럴듯하게 채우지 않는다.

2. CDK `NodejsFunction`과 번들링
3. `esbuild`
4. 깨끗한 CI 설치
5. Vitest 병렬 실행과 자원 경합

## 검증

스킬의 원칙, 절차, 템플릿에 선택 기준과 형식이 일관되게 반영됐는지
확인한다. 기존 문서는 `주요 개념`만 읽은 독자가 뒤따르는 `증상`과 `원인`의
용어 및 실행 흐름을 설명할 수 있는지 검토한다. 변경한 Markdown 파일은
Prettier와 `git diff --check`로 형식을 검증한다.
