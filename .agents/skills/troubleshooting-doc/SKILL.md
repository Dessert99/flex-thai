# 트러블슈팅 문서 작성

해결이 끝난 문제를 나중에 다시 읽고 배울 수 있는 형태로 `docs/troubleshooting/`에 남긴다.

## 원칙

- **지어내지 않는다.** 실제로 관찰한 것만 쓴다. 에러 메시지, 시도한 명령, 확인한 코드 위치는 대화 기록이나 git에서 확인한 것만 옮긴다. 원인을 끝까지 규명하지 못했으면 "미해결"이라고 쓴다. 그럴듯한 추측을 원인 자리에 채우면 문서 전체가 신뢰를 잃는다.
- **읽는 사람은 6개월 뒤의 사용자다.** 이 세션의 맥락을 모른다고 가정하고 쓴다.
- **학습 가치는 교훈과 디버깅 경로에 있다.** 해결 코드만 남기면 git log로 충분하다.
- 문서는 한국어 해라체로 쓰고 식별자·경로·에러 원문은 영어 그대로 둔다.

## 교훈 한 줄

문서 맨 위 blockquote에 일반화한 규칙을 한 줄로 쓴다. 6개월 뒤 색인을 훑을 때 실제로 읽히는 부분이다.

품질 기준 두 가지를 모두 통과해야 한다.

1. 이 버그를 실제로 막았을 만큼 구체적인가
2. 아직 겪지 않은 버그에도 적용되는가

- ✗ 너무 일반적: "환경변수를 조심하자" (아무 행동도 바뀌지 않는다)
- ✗ 너무 구체적: "`mediaPublicKeyPem`에 `.trim()`을 붙여라" (그 버그에만 적용된다)
- ✓ "Zod는 검증만 하고 정규화하지 않는다. 경계를 넘어온 문자열은 정규화를 명시하라"

단순 오타처럼 일반화할 것이 없으면 **교훈 줄을 통째로 생략한다.** 빈 통찰로 칸을 채우지 않는다.

## 번호 문장 규칙

각 섹션 본문은 한 문장씩 끊어 번호를 붙이고, 섹션마다 1번부터 다시 시작한다.

- `원인`과 `어떻게 찾았나`는 인과 사슬로 쓴다. 앞 번호가 뒷 번호의 원인이나 배경이 되게 이어붙인다.
- `증상`과 `재발 방지`는 항목이 병렬이다. **번호는 나열용으로만 쓰고 없는 인과를 꾸미지 않는다.**
- 번호 사이에 논리가 튀면 기록하지 않은 관찰이 있다는 신호다. 그 단계를 채우거나, 확인하지 않았다면 확인하지 않았다고 쓴다.

## 절차

### 1. 재료 모으기

이 세션에서 문제를 해결했다면 대화 기록에서 아래를 추린다.

- 최초 증상과 에러 메시지 원문
- 실패를 재현한 명령
- 시도했다가 아니었던 가설과 그것을 배제한 근거
- 실제 원인과 그 코드 위치
- 최종 수정과 추가한 테스트

세션 밖에서 해결한 문제라면 위 항목을 사용자에게 묻는다. **비어 있는 항목을 상상으로 채우지 않는다.**

관련 커밋이 있으면 `git log --oneline -10`으로 해시를 확인한다.

### 2. 파일 만들기

날짜는 추측하지 말고 `date +%F`로 확인한다.

- 경로: `docs/troubleshooting/YYYY-MM-DD-slug.md`
- slug는 영어 kebab-case로 증상을 요약한다 (예: `cdk-context-pem-truncation`)
- `docs/superpowers/plans/`와 같은 명명 규칙이다

### 3. 템플릿 채우기

````markdown
# {증상 한 줄}

> 교훈: {일반화한 규칙 한 줄}

- 날짜: YYYY-MM-DD · 영역: infra | api | worker | web | packages | tooling · 커밋: {해시 또는 없음}

## 증상

1. {무엇을 하려 했는지}
2. {무엇이 어떻게 실패했는지}
3. {에러 원문은 아래 블록에 그대로 둔다}

    ```text
    에러 원문
    ```

## 원인

1. {표면에서 관찰된 동작}
2. {그 동작을 만든 코드와 메커니즘}
3. {그 코드가 전제했던 가정과 그것이 깨진 지점}

## 어떻게 찾았나

1. {처음 의심한 것과 그렇게 의심한 근거}
2. {그 가설을 배제한 관찰}
3. {다음으로 좁힌 범위}
4. {결정적으로 확인한 지점}

## 해결

1. {실제로 바꾼 것}
2. {함께 검토한 다른 선택지와 버린 이유}
3. {근본 원인을 없앤 것인지 증상만 막은 것인지}

## 재발 방지

1. {추가한 테스트나 검증}
````

- `원인`은 표면에서 근본으로 파고드는 순서로 쓴다. 번호가 하나뿐이면 아직 얕게 판 것이다.
- `원인` 3번의 깨진 가정이 맨 위 교훈의 재료가 된다. 둘이 이어지지 않으면 교훈이 겉돌고 있다는 뜻이다.
- `해결` 3번이 "증상만 막음"이면 `재발 방지`에 남은 근본 원인을 적는다.
- `어떻게 찾았나`에 재현 절차를 흡수시킨다. 재현 자체가 여러 단계로 까다로웠던 문제만 `재현` 섹션을 따로 둔다.
- 헛다리 없이 바로 풀렸으면 `어떻게 찾았나`를 지운다.
- 추가한 테스트가 없으면 `재발 방지`를 지운다.
- 단 `원인`은 지우지 않는다. 이것이 없으면 문서를 쓸 이유가 없다.

### 4. 색인 갱신

`docs/troubleshooting/README.md`의 표에 새 줄을 추가한다. 최신 항목이 위로 오게 한다. 교훈을 생략한 문서는 교훈 칸에 증상을 짧게 적는다.

### 5. 확인

작성한 파일 경로를 사용자에게 보고하고, 사실과 다른 부분이 있으면 알려달라고 한다. 커밋은 사용자가 요청할 때만 한다.
